# 기술 설계 문서

## 1. 구조

```
스마트폰 센서 (SensorManager, 200 Hz 요청)
  → android-app: SampleAssembler (가속도/자이로 페어링) → 40 ms 배치 → WebView
  → web-game: SensorHub → SwingDetector (실시간 상태기계)
  → swing-engine: analyzeSwing (오프라인 분석, 구간·특징·유효성)
  → physics-engine: swingToDelivery (게임 매핑) → deliveryToLaunch (D-plane) → simulateShot (RK4 비행·바운스·구름)
  → web-game: Three.js 연습장 렌더링, 결과 카드
  → (선택) Smart View 화면 미러링 → LG TV
```

### 기술 선택과 이유
| 결정 | 선택 | 이유 |
|---|---|---|
| 게임 엔진 | Three.js (WebGL) + Android WebView | Unity와 Godot은 이 개발 환경에서 설치·라이선스·CI 빌드를 확보하기 어렵습니다. Three.js는 npm만으로 빌드되고, 같은 코드가 브라우저 시험판과 APK에서 함께 동작합니다. |
| 센서 수집 | 네이티브 Kotlin | 브라우저 DeviceMotion은 약 60 Hz이고 기기마다 다릅니다. 네이티브는 200 Hz를 요청할 수 있습니다. |
| 엔진 언어 | JavaScript (ES 모듈) | 앱과 테스트(node --test)가 같은 코드를 사용하고, 빌드 도구 의존이 최소입니다. |
| AndroidX | 사용하지 않음 | 자체 AssetServer(WebViewAssetLoader와 같은 https://appassets.androidplatform.net 방식)와 MediaStore로 대체해, 의존성 없이 CI 빌드를 안정적으로 유지합니다. |
| 학습 모델 | 사용하지 않음 (현재) | 공개 데이터의 자세 특징 모델이 골퍼 간에 일반화되지 않았습니다 (data-research/REPORT.md). 설명 가능한 물리·규칙 기반으로 시작합니다. |

## 2. 스윙 분석 엔진 (`swing-engine/`)

좌표: 안드로이드 기기 좌표계 (x 오른쪽, y 긴 변 위쪽, z 화면 바깥쪽). 가속도는 중력을 포함한 m/s², 자이로는 rad/s 단위입니다.

1. **전처리** (`preprocess.js`): NaN 제거, 정렬, 중복 시간 제거, 실제 샘플링 속도 추정(중앙값 dt), 30 ms 이상 공백 탐지, 포화 탐지(선언된 센서 범위 또는 최대값이 반복되는 구간), 200 Hz 선형 재표본화, 20 Hz 2차 버터워스 필터를 정방향·역방향으로 적용(위상 지연 없음).
2. **활동 구간**: |ω| > 1.2 rad/s인 구간을 찾고, 0.6초 이내 간격은 병합(탑에서 느려지는 구간 포함)한 뒤 에너지가 가장 큰 구간을 고릅니다.
3. **어드레스**: 활동 직전에 |ω| < 0.5이고 ||a|−g| < 1.5인 구간이 0.2초 이상이면 어드레스로 봅니다. 그 구간의 평균 가속도로 중력 방향을, 평균 자이로로 바이어스를 추정합니다.
4. **자세**: 중력을 정렬한 초기 자세에서 자이로를 쿼터니언으로 적분합니다. 스윙 중 가속도는 원심력이 지배하므로 자세 보정에 쓰지 않습니다.
5. **스윙 평면**: 휴대폰 긴 축 방향 성분(전완 회전)을 뺀 월드 좌표 각속도로 PCA를 해서 주축을 구합니다. 다운스윙이 양(+)이 되도록 부호를 맞춥니다.
6. **회전각 θ(t)**: 평면 각속도를 적분합니다. 어드레스에서 0이고 백스윙에서는 음수입니다.
7. **구간**
   - 탑 = θ 최솟값
   - **가상 임팩트 = 탑 이후 θ가 어드레스 각도(+ 설정 가능한 리드 각)로 돌아온 시점**. 최대 가속도만으로 정하지 않고, 기준 자세 복귀, 회전 방향 전환, 연속성을 함께 사용합니다. 최대 각속도 시점과 맞는 정도는 품질 점수에 반영합니다.
   - 피니시 = 임팩트 이후 |ω| < 1.2가 0.15초 이상 지속되는 시점
8. **유효성 규칙** (발사 차단): 데이터 공백, 포화, 충격(연속 샘플 간 |a| 변화 > 50 m/s²), 방향 전환이 4회를 넘는 흔들기, 최대 평면 각속도 < 3 rad/s, 백스윙 회전각 < 35°, 비정상 템포, 임팩트 미도달
9. **특징값과 출처 표시**: 모든 특징값에 출처를 붙입니다. `measured`는 센서 원값, `derived`는 센서값을 결정적으로 계산한 값, `estimated`는 모델 가정이 들어간 값입니다.

### 실시간 단계 감지 (`realtime.js`)
그립 규약: 휴대폰 끝(+y)이 공 쪽으로 비스듬히 아래를 향하고, 스윙은 휴대폰 폭 방향 축(x)을 중심으로 회전합니다. 백스윙은 휴대폰 뒷면 쪽(gx < 0)으로 올라갑니다. 반대로 쥐는 경우를 위해 설정에 "스윙 방향 반전"이 있습니다.

| 단계 | 판정 기준 |
|---|---|
| 어드레스 | 휴대폰 끝이 수평 아래 15~88°이고, 3초(설정 가능) 동안 회전 속도 < 0.35 rad/s, 가속도 편차 < 1.2 m/s². 진행 막대 표시, 완료 시 "삐-삐" 소리와 진동 |
| 백스윙 시작 | 뒷면 쪽 회전(−gx) > 0.8 rad/s가 40 ms 지속되고, x축 회전이 전체의 50% 이상. 앞면 쪽으로 먼저 움직이면 "백스윙은 뒷면 쪽으로" 안내 후 어드레스 재시작 |
| 탑 | 백스윙 회전이 0.4 rad/s 아래로 감속. 그때까지 백스윙 회전각이 30° 이상이어야 함 (미만이면 재어드레스). 탑에서 2초 넘게 멈추면 재어드레스 |
| 다운스윙 | 반대 방향(앞면 쪽) 회전 > 1.0 rad/s |
| 임팩트 | 다운스윙 회전각이 백스윙 회전각의 95%에 도달 (어드레스 각도로 복귀). 이 순간 타격음을 냄. 최대 각속도 < 2.5 rad/s면 발사하지 않음 |
| 피니시 | 회전이 잦아들면 기록 구간 전체를 오프라인 분석 (포화·충격·공백 검사) |

퍼터는 같은 단계를 더 작은 기준값(`PUTT_PHASES`)으로 판정합니다.

### 센서 범위 초과 처리와 스윙 판정 패널
- **가속도 센서**: 범위를 넘어도 발사를 막지 않습니다. 스윙 각도는 자이로로만 계산하고, 가속도는 어드레스 자세와 전환 특징에만 쓰기 때문입니다. 휴대폰 가속도 센서는 보통 ±8g라서 실제 스윙에서는 자주 넘습니다. 범위에 걸린 샘플은 충격 검사에서도 제외합니다.
- **자이로 센서**
  - 범위에 걸린 구간은 앞뒤 샘플로 2차 곡선을 맞춰 복원합니다. 복원값은 범위값 이상, 2배 이하로 제한합니다.
  - 합성 데이터에서 40 rad/s(2000°/s 범위 초과) 스윙을 복원하면 최대 각속도 오차 1.5% 이내, 임팩트 시각 오차 1 ms 이내였습니다.
  - 스윙 중 120 ms보다 오래 걸려 있으면 각도를 믿을 수 없으므로 발사하지 않습니다.
- **판정 패널** (연습장·라운드 화면 왼쪽, "판정" 버튼으로 접기)
  - 시도할 때마다 결과를 바로 보여 줍니다: 발사 여부, 이유(숫자 포함), 단계별 통과 여부(어드레스·백스윙·탑·다운스윙·임팩트), 센서 사용량(최대값/범위), 다음에 해 볼 것.
  - 스윙 중에는 회전·가속 막대가 센서 범위 대비 실시간으로 표시됩니다.
  - 실시간 판정에서 다시 어드레스하게 된 경우(백스윙 방향 반대, 백스윙이 작음, 탑에서 오래 멈춤, 움직임)도 같은 패널에 이유를 표시합니다.

### 페이스 회전(Twist → Square)과 "손 먼저" 전환 — 레슨 영상 반영
- 참고: 사용자가 보낸 레슨 영상 3개입니다.
  1. 휴대폰을 쥔 드릴: 열림(Open) → 비틀기(Twist) → 스퀘어(Square)
  2. 맨손 스윙(BACKWARD/INSIDE): 백스윙에서 손바닥이 뒤로 젖혀지고(열림), 다운스윙에서 되돌아옵니다.
  3. 여성 프로의 필드 스윙: 몸이 돌기 전에 손목(손)이 먼저 내려옵니다.
- **휴대폰 축의 의미**
  - 긴 축 = 샤프트
  - 화면 = 클럽 페이스
  - 긴 축 둘레의 회전 = 페이스 열림/닫힘 (+ = 열림)
- **페이스 회전 경로** (추정)
  - 측정 시점은 탑, 다운스윙 허리 높이(어드레스 각에서 최대 90° 전), 임팩트 세 곳입니다.
  - `squareProgress` = 허리 높이까지 닫힌 비율입니다.
  - 드릴처럼 다운스윙 초반에 비틀어 허리 높이에서 이미 스퀘어면 0.6 이상이고, 임팩트 직전에 뒤집으면(플립) 낮게 나옵니다.
  - 늦게 닫을수록 임팩트 순간 페이스가 빠르게 돌고 있어서, 같은 동작에서도 임팩트 시점에 따라 방향이 흔들립니다. 게임에서는 이를 타격 품질 최대 −12%로 반영합니다(추정).
- **손 먼저 낙하** (측정유래)
  - `dropLeadMs` = 손이 아래로 가속되기 시작한 뒤, 회전 각속도가 최대의 30%에 도달하기까지의 시간입니다.
  - 40 ms 이상이면 좋음, −20 ms 이하면 "몸이 먼저 돎"으로 봅니다.
  - 몸이 먼저 돌면 가파른 전환으로 처리합니다: 경로가 아웃-인이 되고 어택 앵글이 가팔라집니다.
- 합성 스윙 유형을 추가했습니다: `flip`(늦은 닫힘), `open`(비틀지 않음), `bodyfirst`(몸 먼저)
- 판정 패널에 다음을 표시합니다.
  - "페이스 회전: 탑 +60° → 허리 +42° → 임팩트 +4°"
  - 백스윙 열림이 15°보다 적거나 100°보다 많으면 "백스윙 회전" 경고(영상 2)
  - "손 먼저" 항목
  - Twist/Square 조언

## 3. 물리 엔진 (`physics-engine/`)

- 좌표: x는 목표선 오른쪽, y는 위, z는 목표 방향
- 비행: RK4, dt = 2 ms. 중력, 항력 Cd = 0.20 + 0.35·S, 마그누스 양력 Cl = 0.5·S/(S+0.22) (S = rω/v), 스핀 감쇠 τ = 25초, 바람(상대속도)을 포함합니다. 계수 4개는 공개 TrackMan 투어 평균 7개 샷에 맞췄고, 7개 모두 캐리 오차 ±8% 이내입니다 (단위 테스트로 고정).
- 지면: Penner 방식 반발계수 e(vn), 쿨롱 마찰 + 백스핀 체크로 수평 속도를 줄이고, 구름 저항으로 감속합니다. 페어웨이와 러프 파라미터가 다릅니다.
- **D-plane**: 출발 방향 = w·페이스 + (1−w)·경로 (드라이버 w=0.85, 아이언 0.75). 스핀축 = atan((페이스−경로)/스핀로프트).
- 클럽 기준점: TrackMan PGA 평균(클럽·볼 스피드, 발사각, 스핀, 어택 앵글)
- **게임 보정값은 물리와 분리**되어 있습니다 (`game-config.js`): 100% 파워 기준 각속도(11 rad/s), 실력 단계, 파워 상한 105%, 페이스·경로 이득, 방향 보정. 앱 설정에서 바꿀 수 있습니다.
- **손목 동작 모델** (골프 이론과 공개 자료에 맞춘 버전)
  - 휴대폰 자이로에서 계산하는 값 (측정유래)
    - 래그 유지율 = 임팩트 각속도 ÷ 최대 각속도
    - 릴리스 시점 = 최대 각속도 시각 − 임팩트 시각
    - 전완 회전 속도 = 임팩트 ±20 ms 동안 긴축 회전 각속도의 평균
  - **스피드**
    - 이론: 클럽은 손과 함께 도는 강체이므로, 헤드 스피드는 임팩트 순간의 클럽 각속도에 비례합니다.
    - 적용: 이른 릴리스로 임팩트 때 각속도가 이미 줄었다면, 클럽 스피드에 래그 유지율 ÷ 0.96을 곱합니다 (하한 0.75).
    - 참고: 손목 릴리스를 막은 시뮬레이션에서 헤드 속도가 평균 46% 줄었다는 보고가 있습니다 (ISBS 자료).
  - **로프트·스핀** (충돌 기하)
    - 이른 릴리스는 샤프트 리드를 잃게 해 다이내믹 로프트를 늘립니다. 추가 로프트는 완전 캐스팅 기준 5°로 둔 게임 추정값입니다.
    - 스핀 로프트가 Δ만큼 늘면 다음과 같이 바꿉니다.
      - 스핀 × sin(SL+Δ)/sin(SL)
      - 볼 스피드 × cos(SL+Δ)/cos(SL)
      - 발사각 + w·Δ (D-plane 페이스 비중 w: 드라이버 0.85, 아이언 0.75)
      - 스핀축 계산에도 늘어난 스핀 로프트를 씁니다.
  - **방향**
    - 공의 방향은 임팩트 때의 페이스 각으로 정합니다. 휴대폰 긴축 회전각이 기준이고, 전완 로테이션과 왼손목 굽힘·폄이 모두 이 각에 반영됩니다. 손목을 굽히면(보잉) 페이스가 닫히고, 펴면(커핑) 열립니다.
    - 페이스가 닫히는 *속도*(closure rate)는 방향에 쓰지 않고 표시만 합니다.
    - 근거: 투어 선수의 closure rate는 2,200–3,300°/s로 다양하지만 정확도와 상관이 없다고 보고되었습니다 (PING/GOLF.com, S. MacKenzie). 일반 범위는 1,800–3,600°/s입니다.
- **탑 전환 (수직 낙하)과 가속 구간** (게임 모델, 실제 스윙으로 검증 전)
  - 이론
    - 다운스윙은 먼저 손(팔)이 떨어지고 클럽 각(코킹)은 유지되는 전환으로 시작합니다.
    - 클럽은 키네매틱 시퀀스의 마지막 고리이므로, 다운스윙 후반에 속도를 가장 많이 얻어야 합니다.
  - 측정 (측정유래)
    - **전환 낙하 가속도**: 다운스윙 처음 35% 구간에서 휴대폰의 아래 방향 선가속도 평균입니다. 자이로 자세로 가속도를 세계 좌표로 돌린 뒤 중력을 뺍니다.
    - **전환 초반 회전 비율**: 같은 구간에 이미 풀린 백스윙 각의 비율입니다. 크면 탑에서 클럽을 던진 것입니다.
    - **가속 구간 중심**: 회전 에너지가 가장 빨리 늘어난 시점(ω·α 최대)입니다. 탑 = 0, 임팩트 = 1로 표시합니다.
  - 공에 반영 (`game-config.js`)
    - 스피드는 임팩트 각속도를 따릅니다(래그). 가속이 이르면 임팩트 전에 이미 느려지고, 늦으면 아직 덜 빨라진 상태로 맞습니다.
    - 가속 구간이 0.6–0.88이면 좋음으로 봅니다.
      - 이르면(캐스팅): 다이내믹 로프트 최대 +5°, 페이스 최대 −1.5°
      - 늦으면(클럽이 따라오지 못함): 로프트 최대 −3°, 페이스 최대 +4° 열림 (푸시·슬라이스)
    - 탑에서 던지면(초반 회전 비율 0.1→0.3, 낙하가 없을수록 더 나쁨): 경로 최대 −3°(아웃-인), 어택 앵글 최대 −2°
  - 합성 데이터 비교 (드라이버, 정상 184 m 기준)
    - 탑에서 던짐: 169 m, 발사각 +3.8°
    - 이른 가속: 128 m
    - 늦은 가속: 81 m, 오른쪽으로 17 m (푸시 슬라이스)
  - 분석 버그 수정
    - 문제: 천천히 테이크어웨이하면 움직임 시작 부분이 자이로 바이어스 추정 구간에 섞였습니다. 그 결과 백스윙 각이 최대 7° 작게 계산되고, 임팩트가 16 ms 일찍 잡혔습니다.
    - 수정: 바이어스 구간은 각속도가 0.12 rad/s 미만인 구간으로만 제한합니다.
- 검증: 단위 테스트 17개, CaddieSet 1,757샷 비교 (data-research/REPORT.md)

## 4. 안전 설계
- 안전 안내에 동의해야 스윙 모드에 들어갈 수 있습니다.
- 스윙 준비 중에는 전체 화면 터치를 잠급니다. 해제하려면 1초 길게 누릅니다.
- 파워 상한이 있어 세게 휘둘러도 보상이 없습니다. 기준 각속도를 낮게 잡아 작은 스윙으로도 플레이할 수 있습니다.
- 포화, 충격, 데이터 공백, 흔들기가 감지되면 발사하지 않습니다.
- 앱 화면에 "앱만으로 안전을 보장할 수 없음"을 명시합니다.

## 5. 기록 형식
- CSV: `t_s,ax_mps2,ay_mps2,az_mps2,gx_radps,gy_radps,gz_radps`
- JSON: `golf-swing-reader/recording@1`에는 다음이 들어갑니다.
  - id, 참가자 코드, 생성 시각
  - synthetic 여부, 스윙 유형(의도)
  - 샘플 수, 실측 Hz, 단위, 좌표계
  - 기기·센서 정보, 품질(공백·포화·어드레스)
  - 분석 결과(구간·특징·출처)
- 안드로이드 저장 위치: `Android/data/com.wanghanza.golfswingreader.dev/files/recordings/`. Android 10 이상에서는 `Download/GolfSwingReader/`에도 저장합니다.

## 6. 18홀 코스 "단풍 바다 CC" (`course-engine/`)
- **지형**: 바다로 내려가는 산(가우스 형태, 정상 해발 약 200 m)에 fBm 능선을 더한 해석적 높이 함수입니다. 해안선은 정상에서 약 1.1 km 떨어져 있습니다. 렌더러와 공 물리가 같은 함수를 쓰므로, 화면과 물리 사이에 오차가 없습니다.
- **홀 배치**: 홀별 (파, 길이, 방위, 도그레그, 이동 거리) 데이터로 경로를 생성합니다.
  - 전반 9홀은 서쪽 해안과 서쪽 능선을 돌고, 후반 9홀은 동쪽 해안과 동쪽 사면을 돌아 클럽하우스로 돌아옵니다.
  - 파 72(파3 4개, 파5 4개), 전장 6,055 m입니다.
- **코스 조형**: 홀마다 티 → 그린 높이 프로파일을 만들고, 주변 지형을 그 프로파일로 깎거나 메웁니다.
  - 오르막은 평균 7%, 내리막은 15%까지 허용합니다.
  - 그린은 1.5% 기울기의 평면입니다.
  - 이웃 홀 사이 지형은 가중 혼합으로 잇고, 그린과 티는 우선순위를 높게 줍니다.
- **지면**: 티, 페어웨이, 러프, 그린, 벙커, 숲(낙엽), 바다로 나눕니다. 지면마다 반발, 마찰, 구름 저항, 라이 계수(볼 스피드 배율)가 다릅니다.
- **물리** (`physics-engine/src/terrain-flight.js`):
  - 임의 지형에서 착지를 판정하고, 지면 법선 기준으로 반사합니다.
  - 경사 구름은 굴러가는 구의 중력 성분(5/7)으로 계산하고, 경사가 저항보다 크면 공이 멈추지 않고 계속 굴러갑니다.
  - 바다에 들어가면 그 지점에서 종료합니다.
  - 컵 반경 54 mm 안을 공이 1.6 m/s 미만으로 지나가면 홀인입니다.
- **라운드 규칙** (`round.js`):
  - 클럽 추천, 도그레그 조준
  - 바다나 OB: 1벌타 후 원위치
  - 0.6 m 이하 컨시드, 최대 10타
  - 퍼팅 세기: 휴대폰 각속도 5 rad/s에서 25 m
- **검증**: 코스 테스트를 자동으로 돌립니다.
  - 홀 간격 50 m 이상, 전 구간 해발 3 m 이상, 그린 경사 4% 미만, 재현성
  - 직선 샷 봇이 18홀을 완주해 66~95타가 나오는지 (현재 79타)
  - 바다에 빠진 샷의 벌타 처리

### 6-1. 두 번째 코스 "해남 솔바다 링크스" (`course-engine/src/courses/pinebeach.js`)
- **모티브**: 해남 파인비치 골프링크스에 대해 공개된 특징을 참고했습니다.
  - 반도의 바위 절벽 위에 놓인 링크스이고, 바다로 뻗은 작은 곶들이 있습니다.
  - 약 10개 홀이 바다를 따라 놓여 있습니다.
  - 시그니처는 곶에서 곶으로 바다를 건너는 파3(6번, 화이트 티 182 m 보도)입니다. 15번도 바다를 건너는 파3입니다.
  - 해송과 금잔디(조이시아), 수평선의 다도해 섬들이 보입니다.
  - 홀 배치, 거리, 홀 이름은 이 게임에서 새로 만든 것으로, 실제 코스를 복제하지 않았습니다. 공식 명칭과 로고도 쓰지 않았습니다.
- **지형**
  - 육지는 반도 몸체 다각형과 각 홀을 따라 놓인 띠를 합쳐서 정합니다. 바다 건너는 구간은 띠에서 뺍니다.
  - 해안선은 fBm으로 들쭉날쭉하게 만들었습니다.
  - 절벽 위 평지는 해발 약 22–30 m이고, 안쪽은 솔숲 언덕으로 올라갑니다. 해안 쪽은 약 18 m 폭의 급한 바위 절벽으로 바다(−12 m)까지 떨어집니다.
  - 다도해 섬 6개를 넣었습니다.
- **강제 캐리 홀**: 홀 데이터에 `carry: [시작, 끝]`(홀 길이 비율)을 주면 그 구간에는 페어웨이를 깎거나 메우지 않습니다. 원래 지형(바다)이 그대로 남고, 공이 빠지면 1벌타 후 원위치에서 다시 칩니다.
- **수치**
  - 파 72(파3 4개, 파5 4개), 전장 6,419 m입니다.
  - 6번(183 m)과 15번(180 m)은 바다 약 90–100 m를 건너야 합니다.
  - 9개 이상 홀에서 페어웨이 중심선 120 m 안에 바다가 있습니다(테스트로 확인).
- **바람**: 바닷가라서 코스 기본 바람을 1.35배로 정했습니다.
- **화면 테마**
  - 해송: 낮고 넓게, 바람에 기울어진 모양
  - 금잔디 페어웨이·러프, 바위 절벽, 푸른빛 안개
- **코스 엔진 구조 변경**: `createCourse(정의)`가 이름, 홀 데이터, 자연 지형 함수, 경계, 바람 배율, 테마를 받습니다. 홀 데이터는 이동 방식(walk)과 좌표 지정 방식(tee/corner/green)을 모두 지원합니다. 코스 테스트와 봇 18홀 라운드 테스트는 두 코스 모두에서 실행됩니다.
